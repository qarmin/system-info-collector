What the numbers mean

CPU total [%]
Whole-machine CPU use, already divided by the core count, so 100% means every core is busy. Per-process CPU in the table is scaled the same way: a process pinning two cores of twelve reads about 17%, not 200%.
Disk write, device [MB/s]  Disk read, device [MB/s]
What actually crossed the block device, read from /proc/diskstats - the same counters iostat uses. This is the ground truth for "the disk is busy". Partitions and device-mapper targets are excluded so a single write is not counted two or three times.
Process writes, syscall [MB/s]
The sum of what every process wrote through write(), from wchar in /proc/<pid>/io. Charged to the process that made the call, even when the data only reached the page cache and has not touched the disk yet.
Why the two write lines disagree
They measure different moments of the same write. Syscall above device means processes are filling the page cache faster than the kernel is flushing it - the syscall column names the real author. Device above syscall means either writeback catching up on data written earlier, or a writer that never calls write() at all: a process that mmaps its file and stores into the mapping has wchar of zero while its pages still reach the disk and are charged to it. systemd-journald works exactly this way, so it can be responsible for nearly all of a machine's writes while the syscall column shows it as completely idle - sort by Write device to find it. Both lines being low while the disk is busy points at something outside process accounting, such as swap or a RAID resync.
Write syscall / Write device / Write by children (table columns)
Write syscall is that process's own wchar. Write device is its write_bytes - bytes it personally handed to the disk, which for ordinary buffered writes is zero because a kernel flush thread does that part. Write by children is what the kernel folded in from children that exited during the period: Linux adds a reaped child's I/O to its parent, so a process too short-lived to sample still shows up here, against whoever started it. That amount is subtracted from the first two columns, so they stay the process's own work.
I/O wait
How many samples caught the process in state D - uninterruptible sleep, which in practice means blocked waiting for storage. A process high here is a victim of slow I/O rather than its cause.
RSS max and RSS change
Resident memory: the peak within the period, and the difference between its value at the end and at the start. A consistently positive change across several periods is what a leak looks like.
Shape columns
One miniature plot per metric over the selected period, on that row's own scale - they show when within the period something happened, not how much. A single spike, an even stream and a regular pulse all produce the same total but very different shapes.
started / exited / kernel / spawned N
started - first seen after the recording began, rather than already running. exited - gone before it ended. kernel - a kernel thread, hidden from the table by default; they are still recorded because buffered writeback is charged to them. spawned N - started N children during the period, so its write totals may include children too short-lived to be sampled.
Write session / Read session (table columns)
The whole recording, not the selected period: the process's cumulative counter when it was last sampled minus when it was first sampled. Select the whole session and this should agree closely with "Write syscall" - but the two are measured differently and may not match exactly:
  • The very first sample only establishes a baseline, so bytes written before it are in this column but not in the per-tick sum.
  • Bytes the kernel folded in from reaped children are counted here, but deliberately taken out of "Write syscall" and shown under "Write by children" instead.
So this column is the more complete figure for "what did this process account for during the recording", while "Write syscall" is the more precisely attributed one for a chosen slice of it.
Write lifetime / Read lifetime (table columns)
The only two columns that are not scoped to the selected period. They are cumulative wchar and rchar since the process itself started, which for something launched at boot can be days of activity - the same figures a task manager shows as disk read/write totals. A process that is quiet during the recording but has written gigabytes over its life is still worth a look, and only these columns show it; sorting by them finds the long-running heavy writers. Expand a row to see the same process's lifetime and recorded totals side by side.
Totals for the whole recording
The panel above the table compares what the device actually did against what processes admitted to. A large unclaimed remainder means the write did not come from a write() call this recording saw: a process too short-lived to sample, or traffic outside process accounting such as swap, filesystem journalling or a copy-on-write filesystem amplifying the writes.
Idle samples are not stored
A sample is only kept when the process used CPU, moved bytes, or changed memory. Gaps therefore mean "idle, unchanged", which is why average CPU divides by the length of the period rather than by the number of samples present.
